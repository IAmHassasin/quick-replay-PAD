# PAD board solver — feature notes

Status (2026-10-18): **browser extension on dawnGlare** and **Android app Quick Replay PAD 0.1.0**
(screen recognition, Kotlin solver, SOLVE button, `solve` script step) implemented. Repo created from
[`quick-replay`](https://github.com/IAmHassasin/quick-replay) at `a394373`, v0.1.3.
Read [`CLAUDE.md`](CLAUDE.md) first for the existing Android architecture.

## Decisions (owner, 2026-10-18)

- Fully automatic: the user sets the goals beforehand, presses solve, the path is built and
  dragged with no confirmation step.
- First target: the **dawnGlare simulator in the browser extension**, so the owner can watch it.
  Then Android: recognise the PAD gameplay screen from a screenshot, solve, drag.
- The solve logic must run on both web and Android: plain JavaScript in
  [`browser/extension/lib/pad/`](../browser/extension/lib/pad/) and a **Kotlin port** in
  `android/app/src/main/java/dev/quickreplay/pad/` (owner's choice, no extra library). Both must
  return the same paths: `spec/pad-solver-vectors.json` (generated by
  `browser/scripts/pad-vectors.js`) is checked by `browser/test/unit/pad.test.js` and
  `PadSolverTest.kt`. Regenerate it after an intended solver change.
- Android release 0.1.0 is a separate app (`dev.quickreplay.pad`, "Quick Replay PAD") so it installs
  next to upstream Quick Replay. Drag speed is configurable (the owner found 40 ms too fast).
- `solve` is a script step: SOLVE pressed while recording saves the step (not the drag); the script
  copies the PAD setup when REC starts and always replays with it.

Recognition: grid search on a downscaled chroma map (cell centres colourful, inner cell corners
dull), then **edge refinement**: the left/right/top/bottom extent of strongly coloured pixels of
each orb, least-squares fit of left/top/cell. Orbs: hue votes of saturated, bright pixels on a ring
at 33–44 % of the cell around each centre (skins keep the attribute colour on the outer ring).
Tests (`BoardRecognizerTest`): 5 screenshots, 150/150 orbs right, including the watermelon skin;
grid within 0.5 px of the DOM geometry on dawnGlare.

Verified on the emulator (QR_API35, software rendering, dawnGlare in Chrome "Desktop site"):

| Finding | Evidence |
|---|---|
| Before edge refinement the grid was ~6–10 px low (orb highlights); diagonal drags then swapped a side cell (2/2 runs wrong, orthogonal 2/2 right) | dawnGlare "Number of moves" 11 for a 10-move path |
| After refinement diagonal drags are right | 3/3 runs: 10 moves, expected board |
| Drag speed on this emulator: 25 ms/move misses cells, 50 ms right when idle, 100 ms missed 1 cell in 4 replays, **150 ms right in 12/12 replays** | per-loop screenshots of dawnGlare's counter |
| Record "Reset tap, SOLVE" → play 3 loops after changing the app setup | each loop solved 10 moves with the script's setup (row of Light, 100 ms), not the new app setup |
| Solving a board still resolving combos gave wrong paths | fixed by waiting for two identical reads 400 ms apart; loop delay from the wait before SAVE |
| Memory: a `HashSet<Long>` of states caused an OOM (192 MB heap); screenshots were kept alive through the binder callback (+20–30 MB per solve) | after the fixes: heap 2 MB after GC following 4 solves (debug `MEMORY` command) |

Not verified: the real PAD app (not installable on this emulator), physical devices, other skins
than the watermelon screenshot, special orbs (jammer, poison, bombs, locks, blind: recognition
fails on them, so the step stops).

## Implemented (browser extension)

| Part | File |
|---|---|
| Board model, letters, drag path application | `browser/extension/lib/pad/board.js` |
| Match, combo grouping, gravity, cascades (no skyfall) | `browser/extension/lib/pad/matcher.js` |
| Row, Column, 3x3, Cross, L, TPA detection + placements | `browser/extension/lib/pad/shapes.js` |
| Goals, feasibility check, beam search | `browser/extension/lib/pad/solver.js` |
| Read dawnGlare board from DOM, drag with CDP mouse events | `browser/extension/pad-runner.js` |
| Popup panel, service-worker API (`qr:padSolve`, ...) | `popup.*`, `background.js` |

Tests: `browser/test/unit/pad.test.js`, `browser/test/e2e/extension.test.js` (PAD tests use
`test/fixtures/pad.html`, an offline stand-in with dawnGlare's DOM and drag behaviour).

Search: state = (board, cursor); the held orb is always at the cursor. Every start cell, 4 or 8
neighbours, Zobrist hash to drop repeated states, top *W* states per depth by score (1000 per met
goal + target-colour orbs in the best placements − same-colour orbs touching an exact shape −
2 × move distance of the nearest loose orbs (Chebyshev with diagonals, Manhattan without) +
combos; for an unmet combo-count goal also + 2 per touching same-colour pair). A round stops at
the first depth where all goals are met or at `maxMoves`.

**Anytime widening** (2026-10-18): rounds with W = 1000, 4000, 16000, 64000 until `timeLimitMs`
(default 3 s); after the first solution a round only accepts a shorter path (or as long with more
combos). Children are scored by swapping in place; only kept states copy the board (~1.5–2x
faster per round). Node, 3 s budget vs one 1000-wide round: Row L + 5 combos 19 → 15 moves,
7 combos 14 → 11, Cross of Heart 11 → 6, L of Water + Row of Wood 11 → 10; others unchanged.
Trade-off: a solve now uses the whole time limit; lower it in the popup for a faster answer.

**Drag speed**: each mouse event costs dawnGlare ~15–25 ms (jQuery UI re-measures every tile on
mousemove), so speed comes from fewer events (one per 45 px: 2 per straight move, 3 per diagonal)
and a timeline (move *i* ends at start + *i* × time per move, no sleeping when behind). Live
dawnGlare, 4 boards (10–17 moves): 8 px steps took ~1 s; 45 px steps 0.23–0.27 s at 10 ms per
move and 0.49–0.76 s at 40 ms (new default), all with dawnGlare's move and combo counts equal to
the prediction.

## Verified on the live dawnGlare simulator (2026-10-18)

From `pad.js` (v69): orbs are `#tiles .tile[tilecolor]` (`red blue green light dark heart`, also
`poison jammer mortalpoison xbomb spinner`, `black` = empty), cell 90 px; URL `?patt=<letters>`
(`width`, `height` for other sizes); jQuery UI drag, the held orb swaps with each tile its centre
enters, `.cornerblock` areas (20 px) at inner corners suspend swapping; matching = 3+ in a line,
flood fill of matched same-colour orbs into one combo; skyfall **off** by default (matched cells
stay `black`).

Run with the extension in Chromium (Playwright, headless), 80 ms per move: for 5 cases (Row L
with and without diagonals, Row G, 3x3 Dark, 6 combos) dawnGlare's own counter reported exactly
the solver's move count and predicted combo count (e.g. "9 x, Total Combo: 1, Number of moves:
16" for the 3x3), and the board right after the release matched the predicted board.
Diagonal moves through corners did not swap side neighbours.

## Goal

Given a Puzzle & Dragons (PAD) board on screen, find **one orb drag path** that produces the
orb shapes the user asks for, for example:

- a **row of Light** (one combo that fills a whole horizontal line),
- a **3×3 square of Dark**,
- plus other shapes / a minimum combo count,

then show the path and perform it as a single continuous drag with the existing gesture engine.

## Example board (from the owner, dawnGlare PAD Simulator, 6×5)

Letters: `R` Fire, `B` Water, `G` Wood, `L` Light, `D` Dark, `H` Heart. Rows top to bottom.

```
L G H L B B
L R D D G L
B R R L R R
H B R G B L
L B B R R D
```

Counts: L 7, B 7, R 8, G 3, D 3, H 2 (30 orbs).
So "row of Light" (needs 6 L) is possible, but "3×3 of Dark" (needs 9 D) is **not** possible
on this board without skyfall. The solver must check orb counts first and report impossible
goals instead of searching.
Use this board as the first unit-test fixture.

Second fixture: the owner's in-game screenshot (watermelon orb skin), read by eye, `*` = enhanced:

```
L  H* D  G  H* L
H* D  L  B  H* R
G  L  B  R  G  G
G  G  B  H* B  G
H* G  L  H  B  H
```

Counts: L 5, B 5, G 8, H 8, R 2, D 2. Row of Wood is possible (8 G), 3x3 of anything is not.

## PAD rules the solver relies on

Domain knowledge, **not yet verified in this project**. Check each one against the simulator
before relying on it.

- Boards: 6×5 (normal), 5×4 and 7×6 also exist. Keep rows/cols as parameters.
- The player holds one orb and drags it. Every cell the finger enters swaps with the held
  orb. Diagonal moves are allowed (8 directions). There is a move time limit (a few seconds,
  changed by awakenings/leaders). The timer starts on the first swap, not on touch down.
- After release: 3+ same-colour orbs in a straight horizontal/vertical line are matched.
  Matched orbs of the same colour that touch orthogonally form **one** combo.
  Then gravity, then cascades. New orbs (skyfall) are random. The solver ignores skyfall.
- Shapes (each is one combo):

| Shape | Definition | Typical use |
|---|---|---|
| Row | Combo contains a full horizontal line (6 orbs on 6×5) | Row awakenings |
| 3×3 square | Combo is **exactly** 9 orbs in a 3×3 block | Void damage piercer (VDP) |
| Cross | Exactly 5 orbs in a plus shape | Heart cross, cross leaders |
| L shape | Exactly 5 orbs, 3+3 sharing a corner | L-shape awakenings |
| 4 in a line | Exactly 4 orbs | Two-pronged attack (TPA) |
| Column | Full vertical line | Some leader skills (verify) |

## Proposed pipeline (Android)

```
screenshot → board bounds → orb recognition → (user fixes cells) → solver(goal)
          → path preview overlay → user confirms → one swipe gesture
```

1. **Capture.** The service today only injects gestures
   (`res/xml/accessibility_service_config.xml`: `canPerformGestures` only,
   `canRetrieveWindowContent=false`). Options:
   - `AccessibilityService.takeScreenshot()`: API 30+, needs `android:canTakeScreenshot="true"`.
     No extra consent dialog.
   - `MediaProjection`: works on API 26–29, but asks for consent every session.
   - Decision needed: require API 30+ for the solver (simplest), or support both.
2. **Board bounds.** Calibrate once: the user drags a rectangle over the board, stored per
   screen size. Cell = bounds / (cols, rows). Auto-detecting the board is a later step.
3. **Orb recognition.** Orb skins change the picture but keep the attribute colour on the
   **outer ring**: with the watermelon skin the centre of a Light orb is orange, Water is purple
   inside, Wood olive, Dark magenta. So do **not** sample the centre. Plan:
   - Hue of the saturated pixels on a ring (~70–95% of the radius); compare hue ranges, not exact
     hex values (skins are darker / lighter). Heart = pink rounded square filling the cell.
   - Cluster the 30 cells of one board (same orb type = same sprite on a board) and label whole
     clusters, so one odd cell is pulled to its cluster. Mask the corners (`+`, lock markers).
   - Later: per-skin templates saved after a confident read.
   - Enhanced orbs (`+`) are normal movable orbs: base colour + an `enhanced` flag.
   - Gameplay detection: find a regular grid of orbs in the lower half; only solve when every
     cell is classified with high confidence (this is the safety gate, there is no confirmation).
4. **Solver** (pure Kotlin, no Android dependencies, JVM unit tests, like `engine/`):
   - Input: `Board(rows, cols, cells)`, `Goal` list (e.g. `Row(L)`, `Square3(D)`,
     `MinCombos(n)`), options (diagonals on/off, max path length, time budget).
   - Feasibility check from orb counts.
   - **Beam search** over drag paths. State = board + cursor cell + path. Expand to 8
     neighbours, never step straight back. Try every start cell. Keep the top *W* states per
     depth (start with W≈2000–5000, depth ≤ 40, time budget ~1–2 s on a phone; tune with
     measurements).
   - Score = big bonus per satisfied goal + partial progress (Row: most target orbs in one
     row; Square: most target orbs in the best 3×3 window) + combos × w − path length × small.
     Evaluate a state by simulating match → gravity → cascades without skyfall.
   - Output: path as a list of cells, the final board and the combos found.
5. **Preview.** Draw the path (numbered arrows) on a non-touchable overlay. Reuse
   `overlay/PlaybackOverlay` / `TouchMarkers`.
6. **Execute.** Convert the cell path to one `swipe` step of `quickreplay/v1`
   (`points: [{x, y, t}]` at cell centres, see [`script-format.md`](script-format.md)) and play
   it with the existing `engine/Player`. To verify on the simulator / game:
   - the speed at which every crossed cell is still registered (start with ~80–120 ms per cell
     and measure),
   - that diagonal moves through a cell corner do not also swap a side neighbour (aim exactly
     at centres, maybe hold briefly at each centre),
   - that the whole drag fits the in-game move timer.
   Note: the current player replays a swipe with its total duration and does not reproduce
   per-segment speed (README limitation). Continued strokes
   (`StrokeDescription.continueStroke`, API 26) are the way to fix that if needed.

## Suggested code layout

```
android/app/src/main/java/dev/quickreplay/pad/
  Board.kt        Orb enum, Board (rows, cols, cells), parsing the letter format above
  Matcher.kt      match + combo grouping + gravity + cascades (no skyfall)
  Shapes.kt       Row, Square3, Cross, LShape, Tpa, Column detection on a combo
  Goal.kt         goal model + scoring
  Solver.kt       beam search, feasibility check
  PathGesture.kt  cell path → quickreplay/v1 swipe step
  recognize/      screenshot → board (Android-dependent, keep thin)
  ui/             calibration, board editor, goal picker, path preview
```

Write tests in this order: Matcher (combos, cascades), Shapes, Solver on the example board
(row of Light found, 3×3 Dark reported impossible), then PathGesture.

## Existing open-source solvers (reference only)

Found by web search on 2026-10-18. Licences and maintenance **not checked**. Do not copy
code before checking the licence (this project is MIT).

- [matthargett/padopt](https://github.com/matthargett/padopt): JS web solver (fork of kennytm's
  pndopt), screenshot import. Notes that it ignores cascades and timing.
- [pazusoba/core](https://github.com/pazusoba/core): fast core with a priority queue and several
  scoring profiles (combo, colour, shape).
- [toraora/PadPlayer](https://github.com/toraora/PadPlayer): beam search by default, plays via
  MonkeyRunner.
- [senkevinli/PAD-Auto-Solver](https://github.com/senkevinli/PAD-Auto-Solver): ADB capture + OpenCV
  orb detection + automated swipes. Combos only.
- [mloo-sp/pazudora-solver](https://github.com/mloo-sp/pazudora-solver),
  [alexknutson/Combo.Tips](https://github.com/alexknutson/Combo.Tips): heuristic solvers.

## Risk

Automating input in the live game may break the game's terms of service and risk the account.
Decide this before shipping the solver for the real app. A "show path only" mode (the user drags
by hand) avoids automated input completely.
